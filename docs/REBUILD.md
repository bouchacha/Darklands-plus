# Rebuilding DARKLAND.EXE from source

```
python3 -I tools/build.py /path/to/DARKLAND.EXE
```

This takes about 20 seconds after the first analysis run, which takes about one minute. It ends with:

```
rebuilt build/DARKLAND.EXE: 1675637 bytes md5 0d51cc9458a6724e1bd34a9fe0d81e7f
original      : 1675637 bytes md5 0d51cc9458a6724e1bd34a9fe0d81e7f
BYTE-IDENTICAL
```

Requirements: Python 3, `pip install capstone`, and JWasm (build it from
https://github.com/Baron-von-Riedesel/JWasm with `make -f GccUnix.mak`, then set `JWASM=/path/to/jwasm`).

## Pipeline

| step | tool | output |
|---|---|---|
| 1. parse | `tools/rtlink.py` | MZ header, root, 137 RTLink sections and their relocations. `rtlink.py EXE verify` repacks the file byte-identically |
| 2. analyse | `tools/analyze.py` | Recursive-descent disassembly of all 138 images with exact segment frames, overlay vectors resolved, switch tables decoded: 501,542 instructions, 9,697 functions, 483 jump tables, 485 segment regions |
| 3. function DB | `tools/funcdb.py` | `build/analysis/functions.json` / `.csv`: per-function size, callers/callees, C-vs-asm classification, referenced strings |
| 4. emit | `tools/emit_asm.py` | `build/asm/<image>/<image>_<frame>.asm`: one MASM/JWasm file per original segment |
| 5. encode check | `tools/build.py` | Every distinct instruction text is assembled once. Where JWasm encodes differently from the original (for example `sub ax,7` as 83 vs 2D), the instruction is emitted as `db` with the decoded text in a comment |
| 6. assemble | JWasm | `build/obj/*.obj` (OMF) |
| 7. link | `tools/omflink.py` | Places each module at its link-time frame, resolves symbols across all overlays, applies fixups, regenerates every relocation table, rebuilds the RTLink section table and MZ header, then writes the EXE |

## What is symbolic in the generated source

* **All code flow**: near and far calls, jumps, switch tables and overlay vector calls use labels. 492,093 instructions are emitted as real assembly; 9,388 (1.9%) are emitted as bytes for encoding reasons. None of the byte-form ones is a near branch.
* **All segment references**: all 38,650 relocations are regenerated by the linker from `SEG` expressions, never copied.
* **Far code pointers stored in data**: 818 callback-table entries are emitted as `dd label`.
* **Not yet symbolic**: offsets into DGROUP and the far data segments stay numeric. That is the right baseline for a matching decompilation, because data layout stays fixed. The RTLink manager's internal tables also keep numeric frames (`FRM_abs_*`), and 44 self-patching far-jump stubs in `root_047c` (the driver call table) are emitted as bytes.

## Names

`symbols/names.txt` maps generated labels (`sub_<image>_<frame>_<offset>`) to real names. It currently names the C run-time library, the RTLink manager entry points and `_main`. Every name flows into the assembly, the listings and the Ghidra export. Add names there as functions are understood. The rebuild stays byte-identical whatever the names are.

## Linking ported code

The linker accepts any 16-bit OMF object. A module's segment name is mapped to `(image, frame)` in `build/layout.json`, and LEDATA offsets are frame-relative. To replace an assembly function with compiled C:

1. Split its region file at the function boundary.
2. Compile the C with MSC 6 and map its `_TEXT` segment to the same frame at the function's offset.
3. Rebuild and compare.

A matching function has the same size, so the layout doesn't move and the EXE stays byte-identical. That makes the byte-identical check the matching test.
